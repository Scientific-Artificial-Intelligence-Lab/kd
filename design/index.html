    Design

    KD is a platform for discovering partial differential equations from data. Seven algorithms live in it as plugins: five published by our group (SGA-PDE, DLGA-PDE, DISCOVER, EqGPT, LLM4ED) and two external baselines (PySR, PySINDy). The platform owns what is not a scientific decision: reading data, computing derivatives, executing terms, fitting coefficients, keeping records, writing checkpoints, drawing figures, running a batch. Each plugin owns its search and the scientific choices inside it.

    Data is prepared once and an algorithm is chosen by name:

    model = kd.Model(algorithm="sga").fit(data)

    The fitted model carries the equation, the score and the record of the run. Changing "sga" to "discover" changes neither that line nor the way the answer is read.

    Division of responsibility

    How to differentiate the data, how to search, how to score a candidate and which equation to hand back belong to the algorithm. What the seven need identically belongs to the platform.

    Those services are offered rather than imposed. An algorithm that wants its own scientific path takes it: EqGPT runs two of its modes without platform derivatives at all, SGA-PDE and LLM4ED fit candidates with code they brought with them. What a plugin does not opt out of is the small contract that makes it drivable, and a declaration of what it can accept: which equation forms, which data layouts, where its derivatives come from, what its score is called and which direction is better, which parameters survive a resume. Those declarations are readable at runtime through kd.instrument_schemas(), so a program driving the platform, and the parameter tables on this site, work off the same source instead of a table maintained by hand.

    Shared machinery

    Derivatives are the clearest case. kd.PDEDataset holds observations only: fields, axes, and which field-axis-order triple is the left-hand side. Derivatives are computed on demand, by finite differences on the grid or by training a surrogate of the field and differentiating that network, following what the algorithm declared it needs. They could not have been stored in the dataset to begin with: the autograd ones come out of a training run that had not happened when the dataset was written.

    The rest of the machinery under a search is shared the same way: executing a term string into a column of numbers, assembling the design matrix, solving the least-squares problem, computing MSE, NMSE, R² and AIC, training a surrogate network. Six of the operators route through guarded implementations, so a near-zero denominator or an overflowing exponent produces neither an inf nor a nan. An algorithm that arrives writes its search and inherits the rest.

    Shared notation

    Internally the seven carry different things: SGA-PDE searches expression trees, PySR returns SymPy expressions, PySINDy and DLGA-PDE select columns from a candidate-term library. Before an answer reaches the platform it is written as the same term strings (mul(u, u_x), diff_x(diff2_x(u))), and the equation is assembled from terms, coefficients and a left-hand side. Those private structures never leave their own package: results, checkpoints, figures and batch records all carry the shared notation.

    The platform keeps no per-algorithm result format. With one, two equations could only be compared by the string each happens to print, and most of the difference between two such strings is rendering: reorder one KdV candidate library and the same law prints as add(diff_x(diff2_x(u)), mul(u,u_x)) in one run and add(mul(u,u_x), diff_x(diff2_x(u))) in the next. So kd.law_signature reads the set of terms rather than the string, and two equations with the same structure get the same structure_key.

    Score comparability

    Each algorithm hands back its own objective value: SGA-PDE reports AIC, lower is better; DISCOVER reports a reward, higher is better. The two are not the same quantity and there is no conversion between them.

    The platform does not fold them into one score. Two scores are commensurable when the score_kind, the dataset and the scorer all match, and folding changes none of those three, it only hides that they do not match. To compare, refit the candidate terms against the same data and read the nmse from that fit, which is what kd.evaluate_terms does. That is also why best_score_ stays in the algorithm's own units and is never rewritten by the platform.

    Figures from one call

    kd.VizEngine renders from the per-iteration record inside the result object, so this call does not change with the algorithm:

    kd.VizEngine(output_dir="out/kdv").render_all(
    model.result_, algorithm=model.algorithm_, dataset=data
)

    Out comes the set every algorithm shares (convergence, parity, residual distribution and field, the equation and the field it reproduces), the diagnostic panels that algorithm declares as its own, and a single-file HTML report. Nowhere does the engine branch on an algorithm's name; which panels are its own is something the algorithm declares. A figure that cannot be drawn is named in the report's warnings instead of quietly going missing, and an overlay of runs whose scores are of different kinds declines to average them and says so on the figure.

    Checkpoints and resuming

    Point checkpoint_dir at a directory and the run saves its state as it goes, plus a final checkpoint when it ends. kd.load_checkpoint_manifest reads the ledger that directory keeps, so a resume point comes from recorded entries rather than from a glob over filenames.

    What a resume restores is the search state; the configuration comes from the new kd.Model. Each parameter carries a tier the algorithm declared: change a resume-safe one and the new value takes effect, change an init-only one and the resume raises, naming the parameter along with its stored and live values. A parameter with no tier registered is treated as init-only, so forgetting to register one costs a refused resume rather than a silent pass.

    → Parameter tiers and resuming

    Batch studies

    One fit answers one question. Research questions are usually plural: does this hold across seeds, across algorithms, across datasets? kd.harness takes an ordered matrix of entries, each an algorithm with a dataset, a seed and its settings, and runs it into a directory that is sealed on write and re-verified whenever it is reopened. An entry that raises is recorded as a failed outcome and the rest of the matrix still runs.

    The aggregate then comes from those records rather than from notes. Runs are grouped by the canonical set of terms they selected, and each group reports how far the agreement inside it goes.

    Each band uses what is below it, and no algorithm's search is built on another's. Figures sit under the algorithms rather than over them because an algorithm declares its own diagnostic panels out of the drawing layer's descriptors, not the other way round.

    That order is checked rather than described. An import graph is built on every push and matched against this list, and the list is exhaustive both ways: a new module has to be placed in a band, and a new algorithm has to come out independent of the other six. Neither can be left undeclared without failing the build.

    The path of one fit

    The bands above say what may use what. Read in time instead, a single kd.Model.fit passes through five stages, and the search itself is one of them:

    Before
    The caller builds the dataset. It holds observations and nothing derived from them: fields, axes, and which field-axis-order triple is the left-hand side.
    kd.PDEDataseta loader, a file, the Hub or a generatoradded noise, if wanted
    ↓
    Setup
    The fit resolves and checks the left-hand side, reads what the algorithm declared it needs, and assembles that much and no more. An algorithm that declares it needs no derivatives from the platform is given neither those nor an evaluator, and keeps the term executor alone.
    finite differences, or a surrogate network trained and differentiatedterm executorevaluator
    ↓
    Search
    One call to prepare, then the same three steps every iteration. This is the whole of the contract: the platform drives the loop and never decides what happens inside a step.
    propose → evaluate → updatecallbacksone record per iterationa checkpoint per iteration, if a directory was given
    ↓
    Answer
    The algorithm hands back its final candidate; the platform assembles the equation and the record of the run into one object. The fit returns here.
    model.best_expr_model.best_score_model.result_
    ↓
    After
    Figures and an independent re-check are separate calls, made when they are wanted. Neither is a tail stage of the fit.
    kd.VizEnginekd.verify_equation

    How much of the setup stage an algorithm draws on is its own decision, which is what makes those services offered rather than imposed. DISCOVER uses the shared chain throughout: the platform executes and caches the term columns, solves for the coefficients and computes the metrics. PySINDy, PySR and EqGPT are mixed, with the platform building the design matrix and re-scoring the answer while the algorithm's own backend does the coefficient regression. SGA-PDE runs its own pipeline end to end, down to its own sparse regression, and uses the loop and the records and nothing else.
